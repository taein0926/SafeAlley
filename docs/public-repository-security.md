# 공개 저장소 민감정보 점검

## 2026-11-03 점검

GitHub `taein0926/SafeAlley`의 공개 상태를 API로 확인했다.
GitHub·GitLab 원격 브랜치를 가져온 뒤 현재 추적 파일·게시할 신규 파일과
로컬의 모든 ref에서 도달 가능한 Git 이력을 검사했다. 이전 배포 TAR.GZ·ZIP 내부 파일도 검사했다.
게시 전 기존 이력은 146개 커밋·1,414개 파일 blob이었다.

검사 항목은 개인키 헤더, GitHub/GitLab·AWS·Google·Slack·OpenAI 토큰 형식,
JWT, 인증정보가 들어간 URL, 키·비밀번호 대입값과 로컬 `.env`의 실제 비밀값 일치 여부다.
후보 문자열 자체는 출력하거나 공개 보고서에 저장하지 않았다.

검사 범위에서 실제 API 키·비밀번호·SSH 개인키·JWT 노출은 발견되지 않았다.
대입값 후보는 `change-me-for-local-development` 같은 예제값과 합성 테스트 키였다.
이 예제 비밀번호는 운영에 사용하지 않고 설치 시 고유한 값으로 바꾼다.
서버 주소·포트·관리자 사용자명·모델 체크섬은 문서에 포함되어 있으며 인증 비밀값은 아니다.

`.env`, `deployment/.private/`, 비공개 연결 설정·SSH 개인키·DB 백업·모델은
추적 파일과 전달본에 포함하지 않는다. `.gitignore`에 개인키/인증서 저장소 확장자를 추가했고,
패키징 시 주요 토큰 형식과 개인키를 발견하면 파일명만 알리고 생성을 거절하도록 보완했다.

이번 검사는 가져온 ref에서 도달 가능한 이력과 저장소 파일에 한정한다.
삭제된 원격 ref, 다른 사람의 fork·이전 다운로드 사본, GitHub 이슈·Actions 산출물,
VM/PC의 비공개 파일이나 서비스 침투 검사는 포함하지 않는다.
형식을 알 수 없는 임의의 비밀값까지 없다고 보증하는 검사는 아니다.

## 이후 게시·전달 시

- `.env.example`에는 예제와 빈 키 항목만 둔다. 실제 키는 로컬 `.env` 또는 VM `private/service-env/`에서 관리한다.
- `VITE_*`는 브라우저에 공개되는 값이므로 비밀값을 넣지 않는다.
- `git status --short`, `git diff --cached`로 게시 대상을 확인하고 비공개 파일이 추적되지 않는지 확인한다.
- 소스를 먼저 커밋하고 `deployment/package.py --ref <소스커밋> --output <새파일.tar.gz>`로 묶는다.
  기존 파일을 직접 덮어쓰지 않고 검증한 새 압축본과 SHA-256 파일을 함께 교체한다.
- 전달본의 `release.json`과 각 파일 해시를 검사한다. 배포 테스트는 실행 코드와 문서 전체가 checkout과 일치하는지도 확인한다.
- 실제 비밀값 노출을 발견하면 먼저 해당 키를 폐기·재발급하고, 이후 이력·캐시·전달본 정리를 검토한다.
  최신 파일에서 지우는 것만으로 이전 공개 이력의 값이 무효화되지는 않는다.

현재 PC 모델 준비·VM 연결은 [PC AI 운영 안내](../deployment/pc_ai/README.md),
전달본 생성과 VM 업데이트는 [배포 안내](../deployment/README.md)를 따른다.
