# 자연어 경로 요청 해석 품질 기록 (2026-10-01)

> 최신 main 통합 메모: 이 문서의 장소·도로 수치와 실제 경로 예시는 이전 담당자 DB 백업 스냅샷에서 측정한 이력이다. 2026-10-01 최신 main(`6d6232b`)에는 인도 우선 경로 선택과 지도 로딩 개선이 포함되어 있으며, 이번 통합 브랜치에는 그 코드를 유지한 채 자연어 검산·평가셋·추천 근거 안전장치만 추가했다. 최신 공간 DB ZIP은 이 통합 작업에서 복원하지 않았다. 통합 코드 검증은 별도 임시 PostGIS로 백엔드 264 통과·1 건너뜀, 프론트 128 통과 및 빌드 성공이다. 이전 스냅샷의 수치를 최신 DB 현황이나 새 코드의 실사용 품질로 해석하지 않는다.

## 기준 데이터와 범위

DB 통합 검증은 담당자가 전달한 2026-10-01 공간 DB 백업을 별도 Compose 프로젝트 safealley-colleague에 복원한 **스냅샷**을 기준으로 한다. 백업 이후 담당자 컴퓨터에서 바뀐 데이터와 자동 동기화되는 DB는 아니다. 기존 사용자 로컬 DB와 화면(3001)은 덮어쓰지 않았다. 별도 백엔드는 8001, 화면은 3002다. 백업 데이터의 지명·도로망·지표가 실제 서비스의 최신 상태를 보증하지 않는다.

## 처리 흐름과 이번 수정

1. 로컬 Qwen3:4b가 질문을 출발지, 도착지, 출발 시각, 선호 조건으로 먼저 구조화한다. SQL이나 좌표를 생성하게 하지 않는다.
2. Pydantic 스키마가 필드·방향을 검증한다. 서버는 원문에 없는 장소 생성, 명시된 시각 누락, 명백한 부정·허용 표현의 역해석, 지원 지표명과 다른 동의어 등을 제한적으로 검산한다. 규칙은 전체 자연어를 대체하는 Parser가 아니다.
3. 장소 Resolver가 담당자 백업 DB의 장소명/별칭을 조회한다. 동순위 후보가 여러 개면 임의로 선택하지 않는다. 정확히 일치하는 역명과 지하철역 레코드가 하나면 그것을 우선한다.
4. 허용된 rank_routes Tool만 실행하고, 미지원 조건은 다른 지표로 치환하지 않고 unsupported_preferences에 표시한다. 모든 조건이 미지원이면 최종 경로를 선택하지 않는다.

이번에 추가한 검산은 허용 표현(피하지 않아도 된다, 건너도 괜찮다), 비교 표현(짧은 길보다는), 거리 요구와 시설 근접성의 구별, 자정/정오·분 단위 시각, 명시되지 않은 장소의 제거, stairs_count 같은 잘못된 지표명을 실제 Router의 stairs_distance_m로 정규화하는 경우다. 이후 처음 보는 질문의 오류를 줄이기 위해 프롬프트에서 조건의 역할(원하는 기준·허용·무관·비교에서 제외)을 구분하도록 명시했다. 모델이 출력한 조건은 해당 공간 요소가 한 번 언급된 절 안에서 명시적으로 허용되거나 비교에서 제외될 때에만 제거한다. 장소 이름이 원문에 없거나 시각이 없는 질문에서 시각을 만들어 낸 경우도 제거한다. 모델이 먼저 구조화하고 서버가 제한적으로 검산하는 구조이며, 문장별 예외를 계속 추가하는 방식은 피했다. 다만 이 검산도 새로운 표현 전반의 이해를 보장하지 않는다.

## 실행 및 재현

별도 백엔드를 현재 코드로 빌드한 뒤 아래 명령을 실행한다. holdout의 독립 **첫 실행 기록은 11/12**이며 재실행 점수를 새 독립 성능으로 부르지 않는다. 과거 독립 10문장의 첫 기록 7/10도 삭제하지 않고 위 표에 남긴다.

    docker compose -p safealley-colleague exec backend python -m pytest -q tests/unit

    docker compose -p safealley-colleague exec backend python -m evals.evaluate_intent --set holdout --quiet
    docker compose -p safealley-colleague exec backend python -m evals.evaluate_intent --set all --quiet

담당자 백업 DB의 실제 API 검증: '밤에 주안역에서 인천사랑병원까지 계단 없이 CCTV가 많은 길로 가줘'를 8001 API에 요청해 HTTP 200을 받았다. 주안역·인천사랑병원, 시간 null, 계단 회피·CCTV 최대화만 구조화됐고 rank_routes 후보 2개가 반환됐다. 두 후보 모두 DB 기록상 계단 0m여서, 이 결과만으로 계단을 회피해 우회했다고 주장할 수 없다. 출발지가 없는 질문은 임의의 출발지를 만들지 않고 HTTP 422로 중단됐다. 기존 유모차 질문은 stroller_accessibility를 보존하고 no_supported_preferences로 응답해 임의 추천을 피했다. 장소명 주안역은 백업 DB에서 subway_station으로 해석됐다. 이는 담당자 DB **스냅샷**과 로컬 LLM을 함께 쓴 통합 테스트이며, 현장 경로 적합성 검사는 아니다.

## 후속: 비교문의 앞 조건과 선택 조건 분리

처음에는 '경찰서 가까운 길보다 짧은 길'에서 경찰서 접근성을 선택 조건으로 남기는 오류를 확인했다. 이 문장만 겨냥해 경찰서 예외를 추가하지 않고, 'A보다 B'의 **같은 문장 안에서** A에만 나타난 factor는 제거하고 B에서도 다시 언급된 factor는 유지하는 공통 검산을 추가했다. 문장 경계를 확인하므로 앞 문장에서 별도로 요청한 조건은 제거하지 않는다. 예를 들어 'CCTV 많은 길보다 계단 없는 길이 좋지만 CCTV도 많으면 좋겠다'는 CCTV를 유지한다.

수정 전에 새 비교문 대조 10개를 실행한 결과는 **7/10**, 요청하지 않은 조건 추가 3건, 조건 누락 1건, 강제 회피 오검출 1건이었다. 수정 후 같은 10개는 **9/10**, 요청하지 않은 조건 추가 0건, 조건 누락 1건, 강제 회피 오검출 0건이었다. 같은 질문으로 개선했으므로 독립 성능이 아니다. 이후 이 10개를 회귀셋에 편입했다.

전체 169문장 재실행은 **168/169**였다. 출발지·도착지·시각은 각각 169/169, 조건은 168/169이었다. 요청하지 않은 조건 추가 0건, 누락 1건, 방향 오류 0건, 강제 회피 오검출/누락 0건, 중앙값 1.764초, 95백분위 2.323초였다. 남은 오류는 두 문장에 걸쳐 'CCTV도 중요하다. 경찰서 가까운 길보다 짧은 길'을 말할 때 거리 최소화를 빠뜨리는 사례다. 이를 문장 전용 규칙으로 즉시 채우지 않았다. 다른 작성자의 새 문장에서 같은 유형을 확인해야 한다. 전체 결과는 개발·회귀 문장이 섞여 있어 일반화 정확도가 아니다.

## 후속: 복수 문장과 사용자 정정

구조를 분리해 진단했다. 현재는 Qwen3:4b가 Pydantic JSON 스키마에 맞춰 출발지·도착지·시각·선호 조건을 먼저 출력한다. 정규식은 주 해석기가 아니라 출력 조건의 명백한 충돌을 제거하는 후처리다. 따라서 LLM이 아예 빠뜨린 새 조건을 기존 삭제 검산만으로 복구할 수는 없다.

복수 문장 비교 실패를 진단할 때 전체 질문에서는 거리 조건을 빠뜨리는 경우가 반복됐지만, 마지막 비교 절만 따로 해석하면 거리 조건을 추출했다. 그러나 문장별 결과를 단순 합치면 '계단 없는 길. 아니, 계단이 있어도 괜찮아'에서 철회한 계단 회피를 되살릴 수 있다. 그래서 자동 문장 분리·합치기는 적용하지 않았다. '여러 문장을 누적하라'는 추가 프롬프트 지시도 대조 세트 9/10을 개선하지 못해 되돌렸다.

별도 복수 문장 대조 6개를 수정 전 실행하면 **4/6**이었다. 실패는 거리 최소화 누락 1건과 'CCTV 많은 길로. 아니, CCTV는 필요 없어'에서 이미 취소한 CCTV 조건을 남기는 1건이었다. 이 중 후자는 특정 CCTV 문장 전용 예외가 아니라 **같은 factor가 여러 번 언급될 때 마지막 명시적 허용·취소 표현을 확인**하는 공통 후처리로 제거했다. 수정 후 같은 6개는 **5/6**, 요청하지 않은 조건 추가 0건, 조건 누락 1건이었다. 단위 테스트 188개가 통과했다.

6개를 회귀셋에 편입한 뒤 전체 **175문장 재실행은 174/175**였다. 출발지·도착지·시각 각 175/175, 조건 174/175, 요청하지 않은 조건 추가 0건, 조건 누락 1건, 방향 오류 0건, 강제 회피 오검출/누락 0건이었다. 모델 호출 지연 중앙값 1.735초, 95백분위 2.212초였다. 담당자 백업 DB용 API(8001)에서도 'CCTV 많은 길로. 아니, CCTV는 필요 없어'의 최종 preferences가 빈 배열이 됐다. 남은 1건은 여전히 두 문장에 걸친 비교에서 거리 최소화를 빠뜨리는 사례다. 이 회귀 수치를 처음 보는 질문의 정확도로 해석해서는 안 된다.

## 후속: 거리 조건 누락과 검증되지 않은 횡단보도 추천

### rank_routes를 처음 보는 사람에게

`rank_routes`는 AI 모델이 아니라 FastAPI 백엔드에 미리 등록한 경로 추천 Tool이다. Qwen은 자연어를 '도화역→수봉공원, 횡단보도 적게'처럼 구조화하기만 한다. Tool Router는 그 구조를 검증한 후 `rank_routes` 하나를 호출한다. `rank_routes`는 DB의 도로망을 이용해 최단 경로와 조건을 고려한 경로 후보를 생성하고, 각 후보의 거리·계단·건널목 등 측정값을 계산한다. 확인 가능한 조건만 비교해 최종 추천 여부를 결정하고, 지도에 표시할 선·숫자·추천 이유를 API 응답으로 돌려준다. SQL 문장을 Qwen이 만들거나 직접 실행하는 단계는 없다. 횡단보도 수가 `null`이면 0개가 아니라 확인 불가다.

이번 추가 작업은 기존 175문장과 분리한 새 질문 12개를 먼저 작성·고정한 뒤 Qwen3:4b로 첫 평가했다. 첫 결과는 **9/12**였다. 비교문에서 '짧은 길' 또는 '짧고'를 거리 최소화로 추출하지 못한 2건과, 뒤 문장의 '밝기는 상관없다'를 이전 조명 선호의 취소로 처리하지 못한 1건이었다. 같은 실패 문장을 본 뒤 검산 범위를 좁게 보완해 재평가 **12/12**가 됐다. 이 수치는 해당 문장에 대한 회귀 통과이지 새로운 사용자 질문의 정확도가 아니다. 사람 또는 다른 팀원이 작성하고 답을 먼저 확정한 독립 질문은 아직 필요하다.

자연어 처리는 여전히 **Qwen 구조화가 먼저**다. FastAPI 코드의 후처리는 사용자가 명시한 '짧은 길/다른 길보다 짧고/최단 경로'를 모델이 빠뜨렸을 때만 `distance_m/minimize`를 복구한다. '짧은 길보다', '최단거리 말고', '경찰서 가까운 길'은 거리 요청으로 바꾸지 않는다. 마지막 문장에 같은 요소를 '상관없다'고 취소하면 기존 선호를 제거한다. 이 검산도 한국어 전체를 이해하는 범용 Parser가 아니므로, 다른 표현으로 된 첫 질문 평가를 계속해야 한다.

기존 175문장을 재실행할 때 목적지만 말한 '인천사랑병원으로 갈 건데…' 1건에서 모델이 장소를 누락했다. 원문 맨 앞에 명시된 '장소로 갈/이동' 형태의 **문자열만** 목적지로 보존하도록 고쳤다. 출발지는 만들어 넣지 않으며, API는 출발지와 도착지가 모두 있어야 경로 실행으로 넘어간다. 이 실패를 본 뒤 보정한 것이므로 독립 성능 개선으로 계산하지 않는다.

새 12개를 회귀셋에 편입한 뒤 전체 **187문장**을 다시 실행한 결과 **187/187**이었다. 출발지·도착지·시각·조건 각 187/187, 요청하지 않은 조건 추가 0건, 조건 누락 0건, 방향 오류 0건, 강제 회피 오검출/누락 0건이다. 모델 호출 지연 중앙값 1.828초, 95백분위 3.172초였다. 평가 중 다른 모델 평가도 함께 실행돼 지연 수치를 이전 실행과 동일 조건의 속도 비교로 해석하면 안 된다. 187개에는 이전에 보고 수정한 문장이 대다수이므로 **실사용 첫 질문 정확도는 알 수 없다**. 다른 팀원이 작성·정답 확정한 새 질문 묶음은 평가 전까지 코드 수정에 사용하지 않아야 한다.

경로 추천에서는 **부분적인 건널목 탐색 비용**과 **비교 가능한 건널목 수**를 구분한다. 도화역→수봉공원 실제 경로에서 최단 후보는 1,431.25m이고 중심선 대체 구간이 109.03m라 횡단보도 수가 `null`(확인 불가)이다. 맞춤 후보는 1,481.90m이고 기록상 0개이지만, 두 후보의 건널목 수를 비교할 수 없으므로 '횡단보도가 적다'고 확정할 수 없다. 이전에는 부분 비용만으로 맞춤 후보를 `ready`로 선택했으나, 이제 횡단보도 요청만 있으면 `no_supported_preferences`와 `selected_route=null`로 돌려준다. 거리처럼 별도로 비교 가능한 조건도 있으면 해당 조건만 사용한다. UI는 보류 시 첫 후보를 자동 선택하지 않고 '비교용 후보이며 추천 경로가 아님'을 표시한다.

담당자 백업 DB에서 `python -m evals.audit_demo_places`를 읽기 전용 실행했다. OSM 도로 엣지 **15,694**, 보행 메타데이터 적용 **5,268**, 중심선 대체 **1,007**, 횡단 태그 엣지 **140**이다. `public_crosswalks` 테이블은 있으나 공식 점은 **0건**이다. 도화역은 최근접 도로 19.0m, 수봉공원은 0.0m다. 주안역 이름은 지하철역·도움시설 두 기록에 중복되며, 지하철역 기록은 데모 좌표로 최근접 도로 37.3m 및 중심선 대체 링크에 붙는다. 더나눔병원은 최근접 도로 30.0m에 보행 메타데이터가 없다. 좌표-도로 근접성은 실제 출입구 위치, 합법적 횡단, 현장 보행 가능 여부를 증명하지 않는다. 공식 횡단보도 원자료 적재와 네트워크 연결, 역·공원 출입구 검증은 데이터 담당자와 확인해야 한다.

`--check-routes`로 세 장소 쌍의 OSM 그래프 연결도 확인했다. 세 쌍 모두 경로는 생성됐다. 도화역→수봉공원 최단 1,431.25m 중 중심선 대체 109.03m, 도화역→수봉도서관 최단 1,126.53m 중 109.03m, 주안역→인천사랑병원 최단 312.23m 중 **312.23m 전부**가 중심선 대체다. 세 쌍 모두 `crossing_data_available=false`다. 따라서 연결된 경로가 있다는 사실만으로 횡단보도 수나 연속된 보도, 안전한 보행 가능성을 주장할 수 없다. 특히 주안역→인천사랑병원은 실제 역 출입구·보도·합법적 횡단 연결을 우선 검증해야 한다.

재현 명령:

    docker compose -p safealley-colleague exec -T backend python -m pytest -q tests/unit tests/integration
    docker compose -p safealley-colleague exec -T backend python -m evals.evaluate_intent --set new_questions --quiet
    docker compose -p safealley-colleague exec -T backend python -m evals.audit_demo_places
    docker compose -p safealley-colleague exec -T backend python -m evals.audit_demo_places --check-routes

이 작업은 담당자 백업 **스냅샷**을 검사했으며 원 DB나 파일을 수정하지 않았다.
